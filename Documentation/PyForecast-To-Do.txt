Good to-do, but not essential (maybe):

* From my reading/understanding the code is not emitting changes correctly to
    to the QAbstractListModel(s)/QAbstractTableModel(s). When data within an 
    item in the list is changed then list.dataChanged.emit() should be called. 
    When items are added or removed from the list, 
    list.beginInsertRows()/list.endInsertRows() should be called. Currently, 
    list.dataChanged.emit() is being called on essentially every change. 
    
    For example, SavedModels.py->SavedModelList(QAbstractListModel) calls
    its "append(self, model)" function which calls insertRow() which from
    my quick google may not call beginInsertRows/endInsertRows (despite the
    fact that SavedModelList overrides insertRows, then it
    calls dataChanged.emit() which again from my quick google is unnecessary
    because existing data is not changing, a Row is simply being inserted.
    
    I would think that "append(self, model)" would call insertRows with the
    row index rather than calling insertRow separately.

* The code really really really really really needs unit tests. See GitHub
    issue #2 (https://github.com/DOI-BOR/PyForecast/issues/2). 
    There should be unit tests to ensure, at minimum:
        - that reading/writing of forecasts functions
        - web requests function to download data (USGS, NRCS, Hydromet, etc)
        - regression outputs replicate when code is changed
        - forecast outputs replicate when code is changed
        - other critical outputs replicate when code is changed
        - etc...

* More of a periphery comment, but I have seen very few checks/validations
    within functions that they have the data they expect to have to 
    function correctly. Or that while functions execute, calculations are
    executing correctly. This can and will lead to unexpected application
    behavior and application crashes. Both the model generator and generate
    forecast functions should be parsed into smaller functions that do small
    and specific tasks. If there is an error with a task, log it, and inform
    the user as needed.
    
    For example, outside of the 2 try/except/finally
    blocks I implemented to load/save an SQLite forecast, there is 1 
    try/except for plot tick formatting, in the entire codebase!
    
    Another example, once the model generator finishes and shows the models,
    clicking the 'Save' button caused an exception because the code did not
    check if an actual row (model) was selected to save, so index error in code.

* On the other end of the spectrum. Personally, I do not think that Python
    is the proper tool for a full-fledged desktop application. Python packages
    are constantly changing with API breakages, combined with the inherent
    difficulty of packaging a Python application (e.g., PyInstaller, etc.). I
    have PyInstaller functioning, but it required:
        - modifying the Logger class because it was assigning sys.stdout to
            the Logger QObject and calling the classes 'write' function and 
            the PyInstaller generated PyForecast.exe failed stating that the
            object had no 'write' method, I presume because sys.stdout indeed
            has no 'write' method.
        - modifying the model generator to use a QRunnable rather than manually
           managing a QThread. The PyInstaller generated PyForecast.exe would
           simply freeze when trying to run the model generator.
        - loading a V5 pickled forecast works in my development environment, 
            but fails with the PyInstaller generated PyForecast.exe. SQLite
            functions correctly in both environments.
        - Numba JIT usage was causing errors, so it was removed.
    This inconsistency in application behavior in a development environment vs 
    the bundled application is extremely worrisome to the long-term use of the 
    program. My preference would be to move the entire codebase into a compiled 
    language like C# where "bundling" the application is simply "compile", and
    consistency between a development build and release build is guaranteed.
    A framework like Avalonia or Uno could provide a truly cross-platform 
    desktop application and provide long-term program stability.
